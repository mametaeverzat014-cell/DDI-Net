# DATA_INTEGRATION_AUDIT.md — что уже есть до постройки биологического слоя

Дата аудита: 2026-08-28. Проведён **параллельно** идущему эксперименту Фазы A-2;
ни один файл, в который пишут его процессы, не затронут (см. §8).

Цель аудита — не описать репозиторий, а ответить на один вопрос: **что можно
переиспользовать, чтобы не построить второй раз то, что уже работает.**

---

## 1. Существующие модели данных

| Уровень | Где | Ключ | Состояние |
|---|---|---|---|
| Препарат / соединение | `data/tdc_drugbank.py` | `drugbank_id`, `inchikey` | **работает**, 1 705 препаратов |
| Пара препаратов | `data/tdc_drugbank.py::load_pairs` | `pair_key` (упорядоченная) | **работает**, 191 402 пары |
| Молекулярный граф | `features/molgraph.py` | `inchikey` → `MolGraph` | **работает** |
| Граф препарат–препарат | `features/ddi_graph.py` | индекс узла | **работает**, типизированные рёбра |
| Механизм взаимодействия | `data/mechanism.py` | категория + уверенность | **работает**, 0 % непокрытых |
| Препарат → белок | `data/drugcentral.py` | `drug_id` → `gene`/`uniprot_id` | **работает**, 1 228 препаратов |
| Белок ↔ белок | `data/reactome.py` | символ гена / UniProt | **работает** |
| Побочные эффекты | `data/sider.py` | STITCH CID | **загружен, не соединён** |

Ключевой факт: **три из восьми уровней биологической цепочки уже построены**
(`Drug → Target`, `Protein ↔ Protein`, `Mechanism`). Задача не «построить с
нуля», а «подвести под общий канонический слой и добавить ChEMBL».

## 2. Существующие идентификаторы

Реально присутствуют в коде и данных:

| Идентификатор | Где | Покрытие |
|---|---|---|
| `drugbank_id` | корпус TDC | 1 705 / 1 705 |
| `inchikey` | `tdc_drugbank.load_drugs` (RDKit) | 1 705 / 1 705 |
| `canonical_smiles` | там же | 1 705 / 1 705 |
| DrugCentral `struct_id` | `drugcentral.load_structures` | 4 099 записей |
| UniProt accession | `drugcentral` (`ACCESSION`), `reactome` | 100 % строк DrugCentral |
| символ гена | `drugcentral` (`GENE`), `reactome_fi` | 1 457 генов-мишеней |
| STITCH CID | `sider.py` | 1 430 препаратов |
| ChEMBL ID | **отсутствует** | — |
| PubChem CID | `pubchem.py` (клиент есть, сеть закрыта) | 0 |

**Колонка `name` в корпусе — копия `drugbank_id`.** Настоящих названий
препаратов в проекте нет. Это измерено, а не предположено:
`(drugs.name == drugs.drugbank_id).all()` → `True`. Следствие: **соединение по
названиям невозможно в принципе**, и любой адаптер обязан опираться на
структурные идентификаторы.

## 3. Существующие сопоставления DrugBank / TDC

| Сопоставление | Модуль | Способ | Измеренное покрытие |
|---|---|---|---|
| DrugBank ID ↔ InChIKey | `tdc_drugbank` | RDKit из SMILES | 100 % |
| DrugBank ID → DrugCentral | `drugcentral.build_drug_target_table` | точный InChIKey | 1 497 / 1 705 = 87.8 % |
| … → мишень с геном | там же | `STRUCT_ID` | 1 228 = 72.0 % |
| … → узел Reactome | `reactome.pathway_adjacency` | символ гена | 1 214 = 71.2 % |
| DrugBank ID → STITCH | — | **нет** | 0 % |
| DrugBank ID → ChEMBL | — | **нет** | 0 % |

Послабление InChIKey до первого блока даёт +40 препаратов (91.9 %) и
существует как флаг `match="skeleton"`, но **не по умолчанию**: слияние солевых
форм — решение, а не факт.

## 4. Представление RDKit

`tdc_drugbank.py` при загрузке считает: канонический SMILES, InChIKey,
брутто-формулу, молекулярную массу, число тяжёлых атомов; помечает невалидные
структуры флагом `valid` вместо их выбрасывания. Проверяется инвариант «один
DrugBank ID — один SMILES». Пересчитывать это в новом слое не нужно.

## 5. Молекулярный граф

`features/molgraph.py`: атомы — вершины, связи — рёбра, признаки связей
(`ATOM_FEATURE_DIM`, `BOND_FEATURE_DIM`). Не зависит от сплита — структура
молекулы является свойством молекулы. Биологический слой его не трогает.

## 6. Сериализация

Что используется сегодня: CSV (результаты), JSON (гиперпараметры, кривые),
`.tsv(.gz)` (сырые источники), `.npz` (предсказания ансамбля). Parquet **не
используется нигде**, но `pyarrow 25.0.1` уже в `requirements.lock.txt` —
значит выбор Parquet для выжимок ChEMBL не добавляет зависимости.

## 7. Сплиты и загрузчики

`data/split.py` — три схемы (`random_pair`, `drug`, `scaffold`), общий вход
`build_any(scheme, drugs, pairs, seed)`, результат `DrugLevelSplit` с полями
`train_drugs` / `val_drugs` / `test_drugs` и бакетами пар. **Это и есть тот
объект, который биологический слой обязан принимать на вход** — см. §10.

`data/negatives.py::build_dataset` строит размеченный набор; `data/leakage.py`
проверяет отсутствие пересечений по префиксам имён бакетов.

## 8. Тесты

264 теста на момент аудита (не 205 — набор вырос за последние сутки).
Существующие файлы: `test_split`, `test_features`, `test_models`,
`test_leakage`, `test_negatives`, `test_assemble`, `test_eval`,
`test_pair_encoding`, `test_parsers`, `test_tdc_drugbank`,
`test_synthetic_fixture`, `test_repo_hygiene`, `test_adversarial`,
`test_biological_adapters`, `test_mechanism`, `test_debias_analysis`.

`test_repo_hygiene.py` ограничивает набор допустимых символов в

**Файлы идущего эксперимента, которых аудит и вся эта работа не касаются:**
`reports/phase_a2_results.csv`, `reports/phase_a2_curves.json`,

## 9. Куда НЕ надо дублировать

| Уже есть | Не создавать заново |
|---|---|
| `drugcentral.build_drug_target_table` | второй парсер DrugCentral |
| `reactome.load_fi_network` | второй парсер Reactome |
| `sider.load_side_effects` | второй парсер SIDER |
| `mechanism.classify` | третий классификатор механизмов |
| `ddi_graph.assert_no_evaluation_edges` | вторую проверку утечки по рёбрам |
| `split.DrugLevelSplit` | собственное понятие сплита |

Новые адаптеры **оборачивают** эти модули, приводя их выход к канонической
схеме, и не переписывают разбор файлов.

## 10. Куда вставляется биологический граф

Точка вставки одна и она уже определена конструкцией конвейера:

```
split.build_any(...)  ->  DrugLevelSplit
                              |
                              v
              [ БИОЛОГИЧЕСКИЙ ГРАФ строится ЗДЕСЬ ]
                              |
                              v
        features.build_feature_bundle(drugs, split, cfg) -> FeatureBundle
```

`FeatureBundle` — контейнер с полями `graph`, `mol_graphs`, `node_features`.
Биологический граф добавляется как **ещё один источник признаков узла и рёбер**,
строящийся из того же `DrugLevelSplit`. Ничего в существующем `FeatureBundle`
менять не требуется, пока модель его не потребляет.

Критично: `build_ddi_graph` уже принимает решение «какие рёбра допустимы» на
основании обучающих пар и вызывает `assert_no_evaluation_edges`. Биологический
граф обязан следовать той же дисциплине, но она для него **не тождественна** —
см. `docs/BIOLOGICAL_GRAPH_LEAKAGE.md`.

## Отклонение от запрошенной раскладки файлов

Запрошено `data/adapters/*.py`. Адаптеры созданы в **`src/ddinet/adapters/`**.

Причина: `data/` — каталог данных, а не пакет; он не в `sys.path`, части его
дерева перечислены в `.gitignore` (`data/raw/*`, `data/processed/`), и модуль,
положенный туда, не импортировался бы как `ddinet.*` и не покрывался бы
существующими тестами. Раскладка `src/ddinet/adapters/` даёт импортируемость,
единый корень пакета с `ddinet.data.*`, которые адаптеры оборачивают, и
отсутствие риска, что код попадёт под правило игнорирования данных.

## Приложение: что слой даёт после постройки (измерено 2026-08-28)

Аудит выше — снимок «до». Ниже — что получилось, числами из
`reports/biomedical_data_quality.json`.

### Хранилище на текущих данных

| | |
|---|---|
| сущностей | 10 777 |
| утверждений | 79 214 |
| различных отношений | 57 253 |
| отношений более чем с одним источником | **0** |

Ноль в последней строке — не дефект, а факт: DrugCentral даёт препарат → белок,
Reactome даёт белок ↔ белок, они не пересекаются. **Первым источником, который
пересечётся с DrugCentral, будет ChEMBL** — и тогда согласие между источниками
станет измеримым впервые.

| Тип сущности | Штук |
|---|---|
| Gene | 6 234 |
| Protein | 2 446 |
| Drug | 1 228 |
| Enzyme | 798 |
| Transporter | 71 |

| Источник | Утверждений |
|---|---|
| reactome_fi | 37 836 |
| reactome_uniprot | 28 759 |
| drugcentral | 20 960 |

Оба сетевых источника ограничены окрестностью мишеней препаратов: остальная
часть Reactome не может достичь пары препаратов, и материализовать её значило
бы тратить память впустую.

### Что нашёл аудит качества

| Проверка | Найдено | Разбор |
|---|---|---|
| дубликаты утверждений | 12 875 → **4 534** | 8 341 были дефектом адаптера (`gene_encodes_protein` выпускался на каждой строке препарат–мишень, а не один раз на пару). Исправлено. Остаток — свойство Reactome, измерено и записано в DATA_PROVENANCE.md |
| «невозможные» отношения | 77 344 → **0** | не ошибка данных: строки DrugCentral без UniProt-акцессии дают ген как объект. Домен расширен до `PROTEIN_OR_GENE` с обоснованием — символ гена это более грубый ключ к тому же продукту гена |
| висячие рёбра и узлы | 0 | |
| самовзаимодействия | 0 | убираются в списке смежности, в сыром виде сохраняются |
| идентификаторы не в своём пространстве | 0 | |
| конфликтующие знаки | 0 | появятся, когда добавится второй источник по мишеням |
| препаратов без InChIKey в корпусе | 4 | из 1 705; помечены `valid=False` загрузчиком |

Оба крупных числа оказались обнаружением дефекта в **моём** коде, а не в
данных. Это и есть цель аудита: без него оба прошли бы вниз по конвейеру как
правдоподобная статистика.
